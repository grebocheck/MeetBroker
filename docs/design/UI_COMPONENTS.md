# Канонічні UI-компоненти

Цей документ фіксує спільну основу інтерфейсу MeetBroker. Новий екран не
створює власну геометрію кнопок, полів або карток, якщо потрібний стан уже
існує в системі.

Візуальний контекст компонентів визначено в
[актуальній дизайн-системі](DESIGN_DIRECTIONS.md).

## Дії

У React використовується `components/ui/Button`, а не ручне поєднання CSS
класів.

| Варіант | Призначення | Геометрія |
| --- | --- | --- |
| `primary` | головна позитивна дія екрана або форми | похила, із заливкою |
| `secondary` | безпечна альтернативна дія | похила, з контуром |
| `danger` | незворотна або руйнівна дія | похила, червона заливка |
| `ghost` | малопріоритетна локальна дія | похила, без заливки |

Похила форма є стандартом для дій. `shape="soft"` застосовується лише там,
де прямокутна геометрія має предметний сенс, а не як локальне дизайнерське
виключення. Розмір `small` призначений для рядків і карток; звичайний розмір
— для форм та модальних вікон.

Hover-заливка похилої ghost-кнопки малюється лише внутрішнім шаром із тим
самим `--shape-action`. Не можна задавати їй прямокутний hover-фон напряму
або складати ghost-дію вручну з CSS-класів.

## Модальні шари

- модальні вікна монтуються через `components/ui/ModalLayer` безпосередньо
  в `document.body`;
- backdrop завжди перекриває повний viewport, включно з навігацією, блокує
  взаємодію з оболонкою та застосовує однакове затемнення і blur;
- локальний stacking context сторінки не повинен визначати порядок
  модального шару.
- діалог утримує focus, закривається через `Escape`, повертає focus до
  виклику й має доступну назву;
- drawer використовує той самий backdrop-контракт і відрізняється лише
  анімацією та розташуванням panel.

## Поля й selectors

- текстові поля, textarea, native select і `SearchSelect` використовують
  спільні border, surface, focus та error tokens;
- selector із потенційно великим набором має пошук і keyboard navigation;
- помилка пов'язується з полем через `aria-invalid` та `aria-describedby`;
- disabled-стан зберігає читабельний текст і не імітує звичайну secondary
  дію;
- групи взаємовиключних варіантів оформлюються канонічним segmented control
  з `aria-pressed`.

## Навігація й focus

- усі дії доступні в DOM-порядку через Tab;
- `:focus-visible` не прибирається декоративним `outline: none`;
- `InputNavigation` додає послідовне переміщення стрілками між сусідніми
  контролами й не перехоплює звичайне редагування тексту;
- активний маршрут використовує `aria-current`, а icon-only button має
  `aria-label`;
- лічильник сповіщень має окрему доступну назву й візуальне обмеження
  `99+`.

## Editorial-сцени

- page header, фоновий marker і технічна верхня смуга використовують спільну
  вертикальну геометрію;
- декоративний marker завжди `aria-hidden` і не дублює заголовок для screen
  reader;
- великі stage-рамки не додаються навколо простого короткого списку, якщо
  вони не допомагають ієрархії;
- внутрішня календарна або таблична сітка не успадковує зовнішні зрізані
  кути.

## Картки керування

- картка має власну заливку й межу, щоб не зливатися з фоном;
- ідентичність об'єкта, його налаштування та дії візуально розділяються;
- поля не стискаються нижче ширини, за якої значення неможливо прочитати;
- на вузькому екрані блоки переходять у вертикальну структуру без
  горизонтального переповнення;
- destructive-дія не конкурує з основною дією за візуальну вагу.

## Правило розширення

Якщо потрібного варіанта немає, спочатку розширюється канонічний компонент і
документується його семантика. Локальний клас допустимий для розкладки
конкретного екрана, але не для повторного визначення кольору, форми чи стану
базового елемента.
