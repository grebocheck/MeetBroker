# Аудит готовності та усунення високопріоритетних прогалин

## Запит 085 — аудит відповідності конкурсному ТЗ

> Провести дослідження й аудит, визначити проблеми проєкту та стан
> готовності згідно `spec-uk.pdf`.

### Результат

- конкурсні вимоги зіставлено з фактичною реалізацією, тестами,
  контейнерами, README та історією Git;
- підтверджено проходження typecheck, 75 unit-тестів, production build,
  повного smoke і відсутність відомих npm-вразливостей;
- окремо оцінено конкурсну й production-готовність;
- найважливішими прогалинами визначено шестиденний замість семиденного
  розклад, відсутність CI, суперечність dev email verification у README та
  відсутність автоматичного browser regression.

Код у межах аудиту не змінювався.

## Запит 086 — високопріоритетне зміцнення готовності

> Залишити авторське бачення розкладу, але додати акуратний перемикач із
> сімома днями за замовчуванням та автоматичним ущільненням без прокрутки.
> Додати CI навіть для закритого репозиторію, завершити email verification,
> задизайнити листи як сайт і автоматизувати browser regression.

### Результат

- семиденний режим став канонічним за замовчуванням;
- режим «Підігнати» використовує 2–7 колонок відповідно до фактичної
  ширини календаря, не створюючи горизонтального scroll;
- вибір режиму зберігається в local storage, контрол має `aria-pressed` і
  перекладений усіма шістьма мовами;
- для вузького семиденного режиму скорочено підписи дат і прибрано
  непридатні для вузьких колонок написи неробочого дня;
- development email verification дозволяє delivery через worker log без
  SMTP, тоді як production з обов'язковою верифікацією без SMTP завершується
  явною помилкою;
- SMTP-доставка отримала безпечний multipart HTML-шаблон у візуальній
  семантиці MeetBroker та локалізовану CTA-кнопку;
- додано Playwright suite для семи маршрутів і viewport 1440, 1024, 768 та
  390 px;
- перший browser-прогін знайшов обрізану focus-область прихованого file
  input у мобільному профілі; виправлено канонічним visually-hidden
  патерном, повторний прогін пройшов повністю;
- додано компактний GitHub Actions pipeline із quality та integration
  jobs; integration використовує звичайний Compose-стек і міграції
  API-контейнера.
- фінальний smoke виявив короткий 502 після перевідтворення web-контейнера:
  nginx ще використовував попередню upstream-адресу, а Compose вважав web
  готовим одразу після старту процесу; додано web та наскрізний nginx
  healthcheck, після чого `--wait` справді очікує доступності UI й API.

### Перевірки

- web: 46 unit-тестів;
- API: 34 unit-тести;
- Playwright: 8 сценаріїв, 4 viewport-проєкти, усі успішні;
- production API/web build;
- Docker Compose health check;
- повний typecheck, unit, smoke і build виконуються фінальним прогоном.

### Пов'язані коміти

- `f069309` — брендований email і development verification delivery;
- `d32587d` — browser regression та виправлення мобільного file input;
- `58b7450` — CI для quality, smoke і Playwright.

## Запит 087 — задачі середнього пріоритету

> Продовжити рекомендований план і виконати блок середнього пріоритету.

### Результат

- demo seed зроблено повторюваним: він відновлює профілі та ролі трьох
  demo-користувачів, прибирає їхні обмеження й створює рівно три майбутні
  показові бронювання без повторного ввімкнення email-каналів;

  валідації, повного життєвого циклу бронювання, конкурентної боротьби за

  нестабільні побічні ефекти React винесено з render-фази;

## Запит 088 — режими запуску, приймальні тести й модульність

> Зафіксувати конкурсну модель запуску через Docker: окремий DEMO режим із
> вимогами ТЗ та штатний PRODUCTION режим. Додати тести часових поясів,
> email-політик, точності сповіщень і реального мобільного бронювання;
> покращити помилки авторизації; розбити монолітний CSS і найбільші файли
> лише за доречними предметними межами.

### Результат

- додано явну політику `APP_MODE=DEMO|PRODUCTION`; Compose за замовчуванням
  відтворює конкурсне demo-оточення, а прямий запуск API без налаштування
  використовує безпечний production default;
- README відокремлює режим застосунку від опційного demo seed та містить
  точні команди повторного наповнення даними;
- acceptance-тестами зафіксовано різницю реєстрації в DEMO/PRODUCTION,
  email verification policy і перерахунок осі календаря між
  `Europe/Berlin` та офісним `Europe/Kyiv`;
- warning pipeline перевіряється на exact-once постановку в outbox і на
  скасування доставки, якщо будь-яке з двох пов'язаних бронювань уже
  неактивне;
- помилки входу й реєстрації прив'язано до відповідних полів із
  `aria-invalid`, `aria-describedby`, виразним danger-станом і очищенням
  застарілої помилки після редагування;
- додано browser acceptance для цих станів та повний мобільний сценарій:
  відкриття форми, створення реального бронювання через UI, перевірка
  viewport і прибирання тестових даних;
- 6840-рядковий CSS розділено зі збереженням каскаду на foundation,
  schedule/overlays, content components, administration, feature pages і
  responsive; еквівалентність джерела перевірено побайтовим складанням
  секцій;
- `AdminPage` перетворено на 70-рядкову оболонку вкладок, а керування
  бронюваннями й кімнатами винесено у предметні модулі;
- життєвий цикл обкладинок зустрічей винесено з `BookingsService` в
  `BookingImagesService`; транзакційний запис аудиту став спільною
  функцією, а права власника/адміністратора покрито unit-тестами.

### Перевірки

- API: 47 unit-тестів;
- web: 51 unit-тест;
- Playwright: 15 сценаріїв — 3 API integration, timezone acceptance,
  2 auth acceptance, mobile booking і 8 перевірок адаптивного календаря та
  критичних сторінок;
- ESLint, typecheck, production web build і перевірка CSS cascade;
- критичні viewport 1440, 1024, 768 та 390 px без горизонтального
  переповнення.

## Запит 089 — адаптивний маркер розкладу та прийняття запрошення

> Перейменувати режим «Підігнати» на «Авто», виправити обрізання фонового
> слова розкладу на малих екранах і додати в модалку «Моїх зустрічей»
> кнопку прийняття запрошення.

### Результат

- коротку назву автоматичного режиму локалізовано всіма шістьма мовами;
- фоновий маркер розкладу отримав intrinsic width і адаптивний розмір,
  тому зберігає повне слово на desktop, compact, tablet і mobile;
- browser regression перевіряє не лише відсутність overflow сторінки, а й
  рівність `scrollWidth/clientWidth` самого фонового слова;
- учасник із запрошенням у статусі `INVITED` може прийняти його безпосередньо
  в модалці деталей «Моїх зустрічей»;
- дія має pending/error стани, після успіху локально оновлює модалку та
  інвалідує персональний календар, бронювання, розклад і відкриті події;
- окремий E2E створює тимчасову зустріч, запрошує demo-користувача, приймає
  запрошення через UI та видаляє тестове бронювання.

### Перевірки

- API: 47 unit-тестів;
- web: 51 unit-тест;
- 9 цільових Playwright-сценаріїв для чотирьох viewport та invitation flow;
- візуальна перевірка календаря на 823×900 і 390×844;
- ESLint і повний typecheck.

### Пов’язані коміти

- `992e6a3` — автоматичний режим, адаптивний маркер і дія прийняття;
- `fbd46b2` — E2E прийняття запрошення та захист від обрізання маркера.
