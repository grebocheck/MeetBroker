# Розробка MeetBroker v0.2.0

## Запит 098 — повний цикл покращень до `v0.2.0`

> Виконати весь план після аудиту, усунути технічний борг, за потреби
> додати безпечні бонусні можливості й лише після повної готовності
> підготувати реліз `v0.2.0`.

### Режим виконання

- створено довготривалу ціль, що охоплює функціональну коректність,
  security і production readiness, тести, експлуатаційність, accessibility,
  поступовий модульний поділ великих файлів, документацію та фінальний
  реліз;
- робота виконується малими перевірюваними інкрементами через окремі гілки
  й pull request із required checks, без ризикового одномоментного
  переписування стабільних модулів;
- notification worker із реальними SMTP і Telegram credentials не
  запускається під час локальних інтеграційних перевірок.

### Інкремент 1 — uploads і зовнішні сповіщення

- спільний вхідний ліміт зображень зафіксовано як 12 МБ для аватарів,
  кімнат і подій, а Nginx отримав 13 МБ для multipart-метаданих;
- `413 Payload Too Large` тепер має стабільний API-код і локалізоване
  пояснення всіма шістьма мовами;
- smoke-сценарій завантажує валідне зображення розміром понад 4 МБ крізь
  Nginx, тому захищає від повернення старого gateway-ліміту 3 МБ;
- для нових користувачів за замовчуванням активний лише внутрішній канал:
  email і Telegram стали явним opt-in;
- міграція вимикає раніше автоматично активовані email-підписки, не
  зачіпаючи обов'язкові системні листи підтвердження адреси;
- README пояснює обидві політики та єдиний upload pipeline.

### Перевірки інкременту

- `npm run format:check`;
- `npm run lint`;
- `npm run typecheck`;
- `npm test` — 112 тестів;
- `npm run smoke` через свіжий Nginx-контейнер — пройдено;
- worker не був запущений, зовнішньої тестової доставки не виконувалося.

### Коміти

- `9d4b108` — узгоджено ліміти завантажень API і gateway;
- `e252141` — зовнішні notification-канали переведено на явний opt-in.

### Інкремент 2 — startup і transport security

- додано централізовану startup-валідацію URL, портів, boolean-прапорців,
  IANA timezone, cookie name, Telegram-конфігурації та production SMTP;
- API отримав Helmet, а Nginx — канонічні CSP, Permissions Policy,
  Referrer Policy, MIME sniffing і frame-embedding обмеження без
  конфліктних дублікатів від upstream;
- загальний rate limit захищає API від аномальних сплесків, а login,
  register і email verification мають окремі суворіші межі;
- відповідь `429` має стабільний код `TOO_MANY_REQUESTS` і переклади всіма
  підтримуваними мовами;
- Telegram webhook перенесено зі secret у URL на офіційний заголовок
  `X-Telegram-Bot-Api-Secret-Token`; порівняння має сталий час, webhook
  закритий поза режимом `WEBHOOK`, а небезпечний fallback `change-me`
  вилучено;
- режим Telegram без явної конфігурації тепер `DISABLED`.

### Перевірки інкременту

- format, lint, typecheck і 119 unit-тестів — пройдено;
- production dependency audit — 0 відомих вразливостей;
- повний Docker build і smoke — пройдено;
- runtime-перевірка вичерпала login quota, отримала `429` із кодом
  `TOO_MANY_REQUESTS`, після чого API-контейнер було перестворено;
- початковий burst 20/хв помилково об'єднував паралельні demo-входи smoke
  та Playwright; login-межу скориговано до 40 спроб за 5 хвилин із
  п'ятихвилинним блоком і перевірено точною CI-послідовністю
  `smoke → 19 Playwright tests` на двох workers;
- browser-facing та API-заголовки перевірено через Nginx; дублікати
  canonical headers відсутні;
- worker не запускався, зовнішніх доставок не виконувалося.

### Коміти

- `5ac0809` — startup-валідація, security headers і rate limiting;
- `a461d7c` — Telegram webhook переведено на secret header.

### Інкремент 3 — hardened containers і production Compose

- API, worker і web запускаються як користувач `node`, окремий Nginx image
  використовує `nginxinc/nginx-unprivileged` і внутрішній порт 8080;
- application-контейнери мають read-only root filesystem, `cap_drop: ALL`,
  `no-new-privileges`, init, restart policy, graceful stop і контрольовані
  `tmpfs`; uploads лишається окремим writable volume;
- worker отримав healthcheck процесу, а всі п'ять сервісів тепер беруть
  участь у `docker compose --wait`;
- bind mount конфігурації Nginx замінено на відтворюваний image;
- `compose.production.yaml` вимагає production env, вимикає demo seed та
  примусово активує `PRODUCTION`;
- CI перевіряє production Compose merge, non-root UID, read-only rootfs і
  скинуті capabilities кожного application-контейнера.

### Перевірки інкременту

- обидві Compose-конфігурації проходять `config --quiet`;
- hardened images зібрані з нуля, усі healthchecks і повний smoke пройдені;
- підтверджені UID: API/worker/web `1000`, Nginx `101`;
- worker перевірено з примусово вимкненими SMTP і Telegram, після тесту
  зупинено; зовнішніх доставок не виконувалося;
- format, lint, typecheck і `git diff --check` — пройдено.

### Коміти

- `dd51e21` — application stack переведено на non-root hardened images;
- `92e7e5c` — CI та документація фіксують container security boundaries.

### Інкремент 4 — спостережуваність, recovery і зовнішні доставки

Додатковий запит у межах інкременту:

> Покращити дизайн Telegram-сповіщень: поточні повідомлення виглядають
> заслабко, додати доречні емодзі та виразнішу структуру.

- process-only healthcheck worker замінено на атомарний heartbeat із
  перевіркою свіжості, стану та коректності JSON;
- worker відновлює outbox jobs, що лишилися в `PROCESSING` понад десять
  хвилин після аварійного завершення;
- усі переходи статусів outbox оновлюють `updated_at`, а для recovery
  створено частковий індекс;
- окремий адміністративний модуль показує summary, пошук, фільтри й
  пагінацію доставок; вручну повторити можна лише `FAILED`, дія скидає
  retry budget і записується в audit log;
- Telegram отримав локалізований HTML-шаблон із семантичною піктограмою
  типу події, виразним заголовком, брендованим footer і обов'язковим
  екрануванням динамічного тексту;
- додано операторські `scripts/backup.sh` і `scripts/restore.sh` для
  PostgreSQL та uploads із SHA-256 manifest, явним підтвердженням
  руйнівного restore і запуском після відновлення без notification worker.

### Перевірки інкременту

- format, lint, typecheck, 126 unit-тестів і production build — пройдено;
- міграцію `014_outbox_operations.sql` застосовано у чинному demo stack,
  колонку та обидва часткові індекси перевірено в PostgreSQL;
- admin delivery API перевірено через Nginx із реальною admin session:
  summary і пагінація повертають очікувану структуру;
- повний smoke доповнено перевіркою delivery operations response і
  повторно пройдено через Nginx;
- heartbeat перевірено в одноразовому worker-контейнері з примусово
  вимкненими SMTP, Telegram token та update mode; контейнер після тесту
  видалено, зовнішньої доставки не було;
- створено реальний backup, перевірено checksum, `pg_restore --list` і
  tar archive;
- повний restore виконано в ізольованому Compose project з окремими
  volumes і портом: збіглися users, bookings, outbox і uploads, API health
  пройшов; тестовий stack, volumes та тимчасовий backup видалено;
- нову вкладку доставок візуально перевірено у Chromium на широкому
  viewport.
- CodeQL виявив incomplete escaping для backslash у новому `ILIKE` search;
  екранування розширено на `\`, `%` та `_`, додано regression unit-test,
  повторний CodeQL пройшов;
- перший CI browser run проявив стару race condition у calendar E2E:
  `aria-pressed` уже змінювався, поки headings перебували у проміжному
  render state. Миттєвий `count()` замінено на bounded Playwright polling;
  точний wide-сценарій до виправлення окремо пройшов 5/5 локальних повторів.

### Інкремент 5 — критичні browser/API boundaries

- окремі API integration suites фіксують 403 для employee на
  адміністративних маршрутах, відсутність HTTP-керування ролями та
  заборону self-revoke адміністратора;
- RSVP перевіряється для `ACCEPTED` і `DECLINED`: відповідь одноразова,
  повторна спроба повертає `INVITATION_NOT_FOUND`, а відхилена зустріч не
  потрапляє до персонального календаря;
- media pipeline перевіряє невалідне зображення, реальний WebP upload,
  оптимізований WebP response, фізичне видалення заміненого файла,
  повернення до preset-аватарки, 12 МБ ceiling, booking ownership і
  admin-only room image flow;
- браузерний сценарій проходить sidebar стрілками, переходить до theme і
  language controls, відкриває/закриває мовне меню та не дозволяє
  просторовій навігації вийти за межі відкритої модалки;
- додано короткі Firefox/WebKit-проєкти для входу, «Мої зустрічі»,
  розкладу й booking modal; CI встановлює всі три browser engines із
  системними залежностями.

### Перевірки інкременту

- 9 нових API integration сценаріїв — пройдено локально;
- 2 spatial-navigation сценарії — пройдено в Chromium;
- Firefox smoke — пройдено локально;
- WebKit binary завантажено, але локальний Linux host не дозволяє без sudo
  встановити його системні залежності; обов'язкова перевірка виконується
  в ізольованому CI через `playwright install --with-deps`;
- загальна конфігурація містить 32 Playwright-сценарії у 12 файлах.
- повний локальний прогін після численних попередніх тестів вичерпав
  навмисно суворий in-memory login limiter; CI розділено на smoke і
  Playwright етапи коротким restart лише API, щоб скидати ephemeral
  counters без зміни PostgreSQL або послаблення production policy.
- після чистого restart API усі 31 локально доступний сценарій
  (`api-integration`, чотири viewport, timezone, accessibility, spatial і
  Firefox) пройшли паралельно; тридцять другий WebKit запускає CI.

### Інкремент 6 — масштабування відкритих подій і пошуку

- `openEvents`, `joinOpenEvent` і `leaveOpenEvent` вилучено з монолітного
  `BookingsService` у предметний `OpenEventsService`; основний сервіс
  зменшився з 1642 до 1466 рядків;
- `GET /api/bookings/open` отримав параметри `search`, `page`, `limit`,
  стабільне сортування за часом та ID і metadata `pagination`;
- пошук охоплює назву, кімнату й організатора, обмежений 160 символами та
  трактує `%`, `_` і `\` буквально через спільний `escapeLikePattern`;
- UI відкритих подій отримав канонічний search toolbar, загальну кількість,
  окремий empty search state і спільний компонент пагінації; narrow layout
  складає форму в один стовпчик;
- міграція `015_listing_search_indexes.sql` додає `pg_trgm` GIN-індекси
  для users/rooms/bookings search, частковий індекс майбутніх відкритих
  подій і складені attendee/outbox/organizer індекси.

### Перевірки інкременту

- міграцію застосовано в demo PostgreSQL, наявність усіх восьми індексів

- `EXPLAIN (ANALYZE, BUFFERS)` для майбутніх відкритих подій використовує

- повний HTTP/PostgreSQL smoke пройдено;
- сторінку візуально перевірено у Chromium на 1440×1000 і 390×844.
