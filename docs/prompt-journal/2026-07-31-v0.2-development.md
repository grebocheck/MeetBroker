# Розробка MeetBroker v0.2.0

## Запит 098 — повний цикл покращень до `v0.2.0`

> Виконати весь план після аудиту, усунути технічний борг, за потреби
> додати безпечні бонусні можливості й лише після повної готовності
> підготувати реліз `v0.2.0`.

### Режим виконання

- створено довготривалу ціль, що охоплює функціональну коректність,
  security і production readiness, тести, експлуатаційність, accessibility,
  поступовий модульний поділ великих файлів, документацію та фінальний
  реліз;
- робота виконується малими перевірюваними інкрементами через окремі гілки
  й pull request із required checks, без ризикового одномоментного
  переписування стабільних модулів;
- notification worker із реальними SMTP і Telegram credentials не
  запускається під час локальних інтеграційних перевірок.

### Інкремент 1 — uploads і зовнішні сповіщення

- спільний вхідний ліміт зображень зафіксовано як 12 МБ для аватарів,
  кімнат і подій, а Nginx отримав 13 МБ для multipart-метаданих;
- `413 Payload Too Large` тепер має стабільний API-код і локалізоване
  пояснення всіма шістьма мовами;
- smoke-сценарій завантажує валідне зображення розміром понад 4 МБ крізь
  Nginx, тому захищає від повернення старого gateway-ліміту 3 МБ;
- для нових користувачів за замовчуванням активний лише внутрішній канал:
  email і Telegram стали явним opt-in;
- міграція вимикає раніше автоматично активовані email-підписки, не
  зачіпаючи обов'язкові системні листи підтвердження адреси;
- README пояснює обидві політики та єдиний upload pipeline.

### Перевірки інкременту

- `npm run format:check`;
- `npm run lint`;
- `npm run typecheck`;
- `npm test` — 112 тестів;
- `npm run smoke` через свіжий Nginx-контейнер — пройдено;
- worker не був запущений, зовнішньої тестової доставки не виконувалося.

### Коміти

- `9d4b108` — узгоджено ліміти завантажень API і gateway;
- `e252141` — зовнішні notification-канали переведено на явний opt-in.

### Інкремент 2 — startup і transport security

- додано централізовану startup-валідацію URL, портів, boolean-прапорців,
  IANA timezone, cookie name, Telegram-конфігурації та production SMTP;
- API отримав Helmet, а Nginx — канонічні CSP, Permissions Policy,
  Referrer Policy, MIME sniffing і frame-embedding обмеження без
  конфліктних дублікатів від upstream;
- загальний rate limit захищає API від аномальних сплесків, а login,
  register і email verification мають окремі суворіші межі;
- відповідь `429` має стабільний код `TOO_MANY_REQUESTS` і переклади всіма
  підтримуваними мовами;
- Telegram webhook перенесено зі secret у URL на офіційний заголовок
  `X-Telegram-Bot-Api-Secret-Token`; порівняння має сталий час, webhook
  закритий поза режимом `WEBHOOK`, а небезпечний fallback `change-me`
  вилучено;
- режим Telegram без явної конфігурації тепер `DISABLED`.

### Перевірки інкременту

- format, lint, typecheck і 119 unit-тестів — пройдено;
- production dependency audit — 0 відомих вразливостей;
- повний Docker build і smoke — пройдено;
- runtime-перевірка вичерпала login quota, отримала `429` із кодом
  `TOO_MANY_REQUESTS`, після чого API-контейнер було перестворено;
- початковий burst 20/хв помилково об'єднував паралельні demo-входи smoke
  та Playwright; login-межу скориговано до 40 спроб за 5 хвилин із
  п'ятихвилинним блоком і перевірено точною CI-послідовністю
  `smoke → 19 Playwright tests` на двох workers;
- browser-facing та API-заголовки перевірено через Nginx; дублікати
  canonical headers відсутні;
- worker не запускався, зовнішніх доставок не виконувалося.

### Коміти

- `5ac0809` — startup-валідація, security headers і rate limiting;
- `a461d7c` — Telegram webhook переведено на secret header.

### Інкремент 3 — hardened containers і production Compose

- API, worker і web запускаються як користувач `node`, окремий Nginx image
  використовує `nginxinc/nginx-unprivileged` і внутрішній порт 8080;
- application-контейнери мають read-only root filesystem, `cap_drop: ALL`,
  `no-new-privileges`, init, restart policy, graceful stop і контрольовані
  `tmpfs`; uploads лишається окремим writable volume;
- worker отримав healthcheck процесу, а всі п'ять сервісів тепер беруть
  участь у `docker compose --wait`;
- bind mount конфігурації Nginx замінено на відтворюваний image;
- `compose.production.yaml` вимагає production env, вимикає demo seed та
  примусово активує `PRODUCTION`;
- CI перевіряє production Compose merge, non-root UID, read-only rootfs і
  скинуті capabilities кожного application-контейнера.

### Перевірки інкременту

- обидві Compose-конфігурації проходять `config --quiet`;
- hardened images зібрані з нуля, усі healthchecks і повний smoke пройдені;
- підтверджені UID: API/worker/web `1000`, Nginx `101`;
- worker перевірено з примусово вимкненими SMTP і Telegram, після тесту
  зупинено; зовнішніх доставок не виконувалося;
- format, lint, typecheck і `git diff --check` — пройдено.

### Коміти

- `dd51e21` — application stack переведено на non-root hardened images;
- `92e7e5c` — CI та документація фіксують container security boundaries.
