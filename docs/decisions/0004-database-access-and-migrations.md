# 0004. Доступ до PostgreSQL і керування міграціями

Статус: прийнято  
Дата: 2026-07-29

## Контекст

MVP використовує `pg`, параметризовані SQL-запити й власний послідовний
runner для SQL-міграцій. Це вже захищає значення користувача placeholders
`$1`, `$2` і дає транзакції та checksum, але власний runner доведеться
самостійно розвивати: блокування паралельного запуску, dry-run, створення
ревізій, baselining і контроль rollback.

База використовує специфічні можливості PostgreSQL, зокрема
`EXCLUDE USING gist` для остаточного захисту від перетинних бронювань.
Інструмент не повинен змушувати відмовитися від такого SQL.

## Рішення

Використовуємо два окремі шари:

1. `node-pg-migrate` керує версіями схеми як PostgreSQL-аналог Alembic;
2. `Drizzle ORM` поступово стає типізованим runtime-шаром доступу до БД.

### Міграції

- наявні `001_initial.sql` і `002_notification_subscriptions.sql`
  зберігаються як незмінна історія;
- перехідний bootstrap розпізнає таблицю старого runner і лише один раз
  baseline-ить відповідні ревізії в історії `node-pg-migrate`;
- нова й чинна БД після цього використовують одну таблицю історії
  `pgmigrations`;
- `node-pg-migrate` запускається з advisory lock і очікує інший активний
  migration process;
- міграції застосовуються окремим deploy-кроком до запуску API та worker;
- demo seed не є міграцією і вмикається явно конфігурацією середовища;
- production rollback виконується лише для ревізій із перевіреним `down`.
  Для незворотних змін використовується forward fix.

### Runtime-запити

- Drizzle schema описує поточні таблиці, типи й зв'язки;
- значення передаються через query builder або параметризований `sql`
  template;
- конкатенація користувацьких значень у SQL заборонена;
- складні PostgreSQL-запити можна залишати як типізований
  параметризований SQL;
- модулі переносяться поступово, починаючи зі сповіщень;
- один бізнес-сценарій не повинен змішувати старий і новий transaction
  context без адаптера.

### Реалізований рубіж

Notification-модуль і окремий worker повністю використовують Drizzle для
runtime-доступу: список, стани прочитання, підписки, Telegram lifecycle,
transactional outbox, блокування jobs через `FOR UPDATE SKIP LOCKED`,
повторні спроби, адресати та генерація нагадувань.

Схема цього модуля описує також мінімальні типізовані проєкції `users`,
`bookings` і `booking_participants`, потрібні worker. Вона не претендує на
перенесення власності над цими таблицями до notification-модуля.

`DatabaseService.ormFor(poolClient)` створює Drizzle context поверх уже
відкритого `PoolClient`. Завдяки цьому outbox та in-app notification,
створені зі сценарію бронювання, комітяться або відкочуються разом із
чинною `pg`-транзакцією. Це єдина дозволена перехідна межа між двома
runtime-шарами.

Інші стабільні модулі поки залишаються на параметризованому SQL. Нову
runtime-логіку слід одразу писати через Drizzle; наступний наявний модуль
переноситься лише окремим перевіреним інкрементом.

## Чому не Prisma або TypeORM

Prisma не описує частину потрібних PostgreSQL constraints, зокрема
`EXCLUDE`, без ручного SQL. TypeORM додає decorator/runtime metadata й
раніше створював небажані dependency-audit наслідки в цьому проєкті.
Drizzle лишається близьким до SQL, а `node-pg-migrate` підтримує чисті SQL
ревізії.

## Наслідки

- міграційний runner більше не є самописною підсистемою;
- перехід не вимагає одночасно переписувати весь API;
- PostgreSQL залишається джерелом остаточних інваріантів;
- ORM зменшує ризик майбутньої небезпечної побудови SQL, але не замінює
  authorization, validation і raw SQL review;
- на перехідний час у коді співіснують `pg` та Drizzle за чіткою межею
  модулів.
