# MeetBroker

Корпоративний застосунок для бронювання переговорних кімнат. MVP уже
запускається як контейнеризований стек і придатний до наскрізного тестування.

## Швидкий запуск

Потрібні Docker із Compose plugin. З кореня репозиторію:

```bash
cp .env.example .env
docker compose up -d --build
npm run smoke
```

Застосунок: [http://localhost:8080](http://localhost:8080)

Демонстраційні облікові записи:

| Рівень        | Email                    | Пароль       |
| ------------- | ------------------------ | ------------ |
| Адміністратор | `admin@meetbroker.local` | `Admin123!`  |
| Користувач    | `user@meetbroker.local`  | `User12345!` |
| Користувач    | `anna@meetbroker.local`  | `User12345!` |

Міграції застосовуються API-контейнером через `node-pg-migrate` перед
запуском NestJS. Worker очікує healthy API, тому не починає обробку до
завершення міграцій.
Ця схема розрахована на один API instance у поточному Docker Compose. Для
production із кількома replicas міграції слід запускати окремим deployment
job, який використовує той самий API image, а не збирає власний.

Демонстраційні дані створюються лише з `SEED_DEMO_DATA=true`, яке вже
вказане у `.env.example`; у production цю змінну потрібно вимкнути.
Повторний запуск є безпечним і повертає три demo-профілі, їхні ролі та три
майбутні бронювання до детермінованого стану без дублювання. Матриця
користувацьких каналів сповіщень при цьому не скидається, щоб seed випадково
не ввімкнув email-розсилку. Для реальної інсталяції також потрібно змінити
паролі БД, webhook secret і не використовувати демонстраційні облікові дані.

Політика підтвердження адреси налаштовується для всієї інсталяції:

```dotenv
EMAIL_VERIFICATION_REQUIRED=false
```

Значення `false` зручне для локального demo: нові профілі одразу отримують
позначку підтвердженого email, а зміна адреси застосовується одразу після
перевірки поточного пароля. Значення `true` є безпечним стандартом, якщо
змінна відсутня: реєстрація та зміна адреси створюють одноразове посилання на
24 години і ставлять системний лист у transactional outbox. У production
потрібно налаштувати `SMTP_HOST` та інші `SMTP_*`; без SMTP API поверне явну
помилку й не створюватиме запит, який неможливо підтвердити. У development
SMTP не обов'язковий: worker виведе повний лист і verification URL як
`[dev-email]` у свій журнал. Зміна змінної вимагає перезапуску `api` та
`worker`.

Реальна SMTP-доставка надсилає multipart-лист: текстову версію та
адаптивний брендований HTML-шаблон MeetBroker. Динамічний текст
екранується, а verification URL додатково виводиться як локалізована
call-to-action кнопка.

Для SMTP submission на порту `587` використовуйте
`SMTP_SECURE=false` — STARTTLS буде узгоджено після підключення. Для
implicit TLS на порту `465` використовуйте `SMTP_SECURE=true`. Невідповідна
пара зазвичай завершується TLS-помилкою `wrong version number`.

Для `TELEGRAM_WEBHOOK_SECRET` згенеруйте окремий криптографічно випадковий
секрет:

```bash
node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"
```

Скопіюйте отримане значення в локальний `.env` замість `change-me`. Не
додавайте `.env` або згенерований секрет до Git. Після зміни Telegram чи SMTP
налаштувань перезапустіть процеси, які їх використовують:

```bash
docker compose up -d --force-recreate api worker
```

Спосіб отримання Telegram updates задається явно:

```dotenv
TELEGRAM_UPDATE_MODE=POLLING
```

`POLLING` призначений для локального demo: worker використовує Bot API
`getUpdates`, тому `localhost` не потребує публічного HTTPS webhook.
`WEBHOOK` призначений для production із доступним з інтернету
`APP_ORIGIN`; webhook треба зареєструвати на
`/api/notifications/telegram/webhook/<TELEGRAM_WEBHOOK_SECRET>`.
`DISABLED` повністю вимикає отримання команд ботом. Polling і webhook не
можуть працювати для одного бота одночасно.

Підключення з профілю створює одноразовий token на 10 хвилин і показує
керований діалог: прямий `tg://` deep link для встановленого застосунку,
fallback через `t.me` та копіювання посилання. Після натискання Start бот
підтверджує прив'язку повідомленням, а профіль автоматично оновлює статус.

Корисні команди для схеми:

```bash
npm run db:migrate
npm run db:migrate:status
npm run db:migrate:create -- add_room_equipment
```

Локальні команди очікують `DATABASE_URL`. Для бази всередині Compose status
можна виконати одноразовим API-контейнером без запуску сервера:

```bash
docker compose run --rm api \
  npm run db:migrate:status:prod --workspace @meetbroker/api
```

Версіями схеми керує лише `node-pg-migrate`; Drizzle не генерує й не
застосовує міграції. Notification API та worker уже повністю використовують
типізований Drizzle runtime-шар. Решта стабільних модулів поки працює через
параметризований `pg` і переноситься лише окремими інкрементами. Нова
runtime-логіка має використовувати Drizzle.

### Керування адміністраторами

Роль і доступ адміністратора не змінюються через вебінтерфейс або HTTP API.
Це окрема операторська дія з доступом до серверного середовища та
`DATABASE_URL`. У запущеному Compose-стеку використовуйте CLI всередині
API-контейнера:

```bash
docker compose exec api node apps/api/dist/database/admin-cli.js \
  promote user@example.com
docker compose exec api node apps/api/dist/database/admin-cli.js \
  demote admin@example.com
docker compose exec api node apps/api/dist/database/admin-cli.js \
  revoke admin@example.com "Зміна відповідального адміністратора"
docker compose exec api node apps/api/dist/database/admin-cli.js \
  restore admin@example.com
```

CLI не дозволить позбавити систему останнього активного адміністратора,
запише дію до журналу аудиту з джерелом `CLI` та під час відкликання доступу
завершить активні сесії. Для звичайних користувачів відкликання і відновлення
доступу доступні адміністратору в розділі «Користувачі».

## Що входить до MVP

- канонічний семиденний календар від вибраної дати, перемикач адаптивного
  режиму на 2–7 днів без горизонтальної прокрутки й захищене від перетинів
  бронювання;
- щоденні та щотижневі серії бронювань з атомарним створенням, одиничними
  винятками й скасуванням вибраної та наступних подій;
- запрошення, відповіді учасників і відкриті заходи;
- профілі, власні фото та готові аватари;
- верифікація, схвалення адміністратором і тимчасові capability-обмеження;
- робочі години та дні кімнат, технічні блокування, каталог бронювань і
  примусове скасування адміністратором з аудитом;
- адміністративне редагування чужих бронювань із причиною, атрибуцією в
  сповіщеннях і пошуковим журналом ключових подій;
- адміністративний override недоступності кімнати з обов'язковою причиною;
- центр сповіщень, email і Telegram через transactional outbox;
- одноразові нагадування про початок і про зайнятий наступний слот перед
  завершенням бронювання;
- матриця налаштувань «група сповіщень × канал» і розширюваний контракт
  `NotificationChannel`;
- адаптивний інтерфейс із компактним мобільним календарем, світла/темна тема
  та повні типізовані каталоги українською, англійською, німецькою,
  іспанською, французькою та японською мовами;
- окремі контейнери PostgreSQL, API, worker, web і Nginx.

## Перевірки

```bash
npm run lint
npm run format:check
npm run typecheck
npm test
npm run build
npm run smoke
npm run test:e2e
```

`smoke` очікує запущений стек на `http://localhost:8080` і перевіряє UI,
health, вхід, кімнати, створення/скасування бронювання, відкриті події,
матрицю сповіщень, усі чотири capability-політики, життєвий цикл
повторюваного бронювання та адміністрування. Окремий псевдонім
`npm run test:integration` додатково підкреслює, що це наскрізна перевірка
реального HTTP API та PostgreSQL, а не unit-тест із моками.

Критичний інтеграційний сценарій також перевіряє відмову для минулого часу й
часу поза робочими годинами, заборону скасування чужого бронювання та
конкурентне створення одного слота двома користувачами.
Його можна запустити окремо, не виконуючи browser-проєкти:

```bash
npx playwright test --project=api-integration
```

Для серії smoke додатково перевіряє три щотижневі події, одиничне
редагування без зміни сусідів і скасування вибраної та всіх наступних подій.

`test:e2e` очікує запущений стек і встановлений Chromium:

```bash
npx playwright install chromium
npm run test:e2e
```

Playwright перевіряє сім основних маршрутів на ширинах 1440, 1024, 768 і
390 px: відсутність runtime-помилок, горизонтального overflow, обрізаних
інтерактивних контролів, а також семиденний і адаптивний режими розкладу.

GitHub Actions workflow `.github/workflows/ci.yml` має два послідовні jobs:
перший перевіряє ESLint, Prettier, типи, unit-тести й production build,
другий підіймає звичайний Compose-стек, виконує smoke, ізольовані API та
browser regression сценарії. Міграції виконує той самий API-контейнер,
окремий migration image або повний дубльований build context не створюється.

Основні сторінки web-застосунку завантажуються окремими route chunks.
Початковий production JS не містить наперед календар, профіль і важку
адміністративну панель; для переходу між чанками використовується спільний
локалізований loading state.

## Час і робочі години

Усі моменти часу передаються API як ISO 8601 і зберігаються PostgreSQL у
`timestamptz`, тобто як UTC-моменти. Інтерфейс форматує їх у IANA-поясі
користувача, який початково визначається браузером і може бути змінений у
профілі. Робочі години, робочі дні й недоступність перевіряються окремо в
`Europe/Kyiv`, тому зміна поясу користувача не змінює офісне правило.

## Перетини та конкурентне бронювання

Інтервали трактуються як напіввідкриті `[start, end)`: бронювання
`10:00–11:00` і `11:00–12:00` є сусідніми та не конфліктують. API виконує
серверні перевірки, а транзакція бере PostgreSQL advisory lock на кімнату.
Остаточним захистом залишається constraint `EXCLUDE USING gist` для активних
бронювань. Тому навіть два одночасні запити не можуть створити два записи
для одного слота: один завершується успішно, інший отримує `409 SLOT_TAKEN`.

## Реалізовані бонуси специфікації

- Docker Compose із Nginx, web, API, worker і PostgreSQL;
- підтвердження email із dev-посиланням у серверному журналі;
- захист від конкурентного бронювання на рівні транзакції та БД;
- фільтр переговорних за мінімальною місткістю;
- щоденні й щотижневі повторювані бронювання;
- одноразове внутрішнє попередження перед зайнятим наступним слотом;
- наскрізний інтеграційний smoke для критичних API-сценаріїв;
- Playwright browser regression для чотирьох класів viewport;
- адаптивний інтерфейс із семиденним та автоматично ущільненим календарем.
